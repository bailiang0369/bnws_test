# 币安现货 vs U本位合约 WebSocket 推送时序差 —— 实测结果总结

- 标的：BTCUSDT
- 采集端点：现货 `wss://stream.binance.com:9443/ws/btcusdt@<stream>`，合约 `wss://fstream.binance.com/ws/btcusdt@<stream>`
- 采集脚本：`latency_probe/spread_probe.py`（双线程独立连接、断线重连、回调第一时刻打 `time.perf_counter()` 戳、异步落盘 JSONL；每 60s 通过 `/api/v3/time` 与 `/fapi/v1/time` 做 NTP 式往返测时钟偏移）
- 分析脚本：`latency_probe/analyze_spread.py`
- 采集时间：2026-10-09（本机出口网络，非交易所同机房）
- 原始数据：`latency_probe/data/*.jsonl`（体积较大，已加入 `.gitignore`，不入库）

## 一、要回答的两个问题

1. **同一时间戳**的推送，两市场到达本地的时间差会不会很大（例如 >50ms）？
2. 同一时间戳的数据，是否**总是**某一个市场先到？

## 二、重要前提发现：两个市场的 bookTicker 根本没有共同时间戳

| 流 | 现货字段 | 合约字段 | 能否按"同一时间戳"配对 |
|---|---|---|---|
| `@trade` | `T` = 成交毫秒戳 | `T` = 成交毫秒戳 | ✅ 可以，且能做到成交级精确对齐 |
| `@aggTrade` | `T` = 成交毫秒戳 | `T` = 成交毫秒戳 | ✅ 可以 |
| `@bookTicker` | **无任何时间戳字段**（只有 `u,s,b,B,a,A`） | `E`/`T` = 毫秒戳 | ❌ 不存在"同一时间戳"，只能用事件代理对齐 |

所以严格意义上"同一时间戳比较"只对 trade / aggTrade 成立。对 bookTicker 我们改用**口径B**：把"最优买价档位发生跳变"视为同一次市场冲击在两个市场的响应，按跳变时刻 ±500ms + 价格 z-score 容差配对。

## 三、实测结果

### 1) `@trade` 流（口径A'：两侧成交时间戳 T 完全相等，n=118；口径A：最近邻 ±2ms，n=1301）

| 指标 | 口径A' (T 精确相等) | 口径A (±2ms 最近邻) |
|---|---|---|
| \|到达差\| p50 | 0.6 ms | 3.6 ms |
| \|到达差\| p90 | 7.9 ms | 17.6 ms |
| \|到达差\| p99 | 42.7 ms | 43.0 ms |
| \|到达差\| max | 44.3 ms | 56.2 ms |
| **>50ms 占比** | **0.00% (0/118)** | **0.08% (1/1301)** |
| 先到方 | 现货 71.2% / 合约 28.8% | 现货 62.1% / 合约 37.9% |
| 中位差(正=合约先到) | −0.30 ms，95%CI [−0.66, −0.19] | −1.65 ms，95%CI [−1.85, −1.40] |
| 符号检验 p | 4.7e-06（显著） | 2.5e-18（显著） |

端到端推送延迟（`t_recv − 事件时间戳 − 服务器时钟偏移`，含本机到币安服务器的网络单程）：
- spot：p50 ≈ 31 ms，p90 ≈ 44 ms，p99 ≈ 58 ms
- futures：p50 ≈ 33.5 ms，p90 ≈ 47 ms，p99 ≈ 81 ms

两服务器相对本机时钟偏差 ≈ +0.3 ms（可忽略）。

### 2) `@bookTicker` 流（口径B：买价跳变事件配对，n=129）

| 指标 | 值 |
|---|---|
| \|到达差\| p50 | 27.7 ms |
| \|到达差\| p90 | 216.5 ms |
| \|到达差\| p99 / max | 488 ms |
| **>50ms 占比** | **39.5% (51/129)** |
| 先到方 | 合约 50.4% / 现货 49.6% |
| 中位差 | +1.73 ms，95%CI [−5.09, +6.86] |
| 符号检验 p | ≈1（**无系统性偏向**） |
| 消息量 | 合约 60845 条 vs 现货 20288 条（约 3:1） |

合约侧 bookTicker 端到端延迟：p50 ≈ 40 ms，p90 ≈ 80 ms，p99 ≈ 151 ms（现货侧无时间戳，无法计算绝对延迟）。

## 四、结论

1. **成交类事件（trade/aggTrade）两市几乎同步**：以真实成交时间戳为锚，两市场到达本地差异中位数 <1ms，p99 ~43ms，>50ms 属长尾小概率（本次样本 0~0.08%）。方向上**现货系统性略快于合约约 0.3~1.7ms**（统计显著），但幅度远小于 50ms，不是"总是某市场先到"，而是"大概率现货稍早"。
2. **盘口推送（bookTicker）不可用于时间戳对齐**：现货侧不带时间戳；即便用价格跳变做事件代理，两市错位也明显更大（p50≈28ms，p90≈217ms，近 40% 超过 50ms），且先后顺序无稳定偏向——因为两个市场的簿更新本身就不是同一个事件，触发时机由各自撮合引擎独立决定。
3. **工程含义**：
   - 需要跨市场"同一事件"时，**以 `@trade`/`@aggTrade` 的成交时间戳为唯一可靠锚点**；
   - `@bookTicker`/深度数据应作为**带新鲜度(age)标签的状态快照**使用，取己方最新值并把 staleness 作为特征或水位线过滤条件，不要期待它能与另一市场对齐；
   - 上面所有绝对延迟数值都受本机出口网络影响（p50 30ms 级别主要是"你到币安服务器"的单程耗时）。若要得到接近交易所侧真相的结论，需把探针部署到与币安同区域（如 AWS 东京 ap-northeast-1）再跑一遍。

## 五、复现方式

```bash
# 采集（建议 ≥1 小时，覆盖活跃时段）
python3 latency_probe/spread_probe.py --symbols btcusdt --streams trade     --duration 3600
python3 latency_probe/spread_probe.py --symbols btcusdt --streams bookTicker --duration 3600

# 分析
python3 latency_probe/analyze_spread.py latency_probe/data/probe_XXXX.jsonl --tol-ms 2 --gap-threshold 50
```

输出包含：配对口径说明、|到达差| 分位数与 >阈值占比、先到方计数 + 符号检验 p 值 + bootstrap 置信区间、各市场端到端延迟分布、按分钟的中位差走势。
